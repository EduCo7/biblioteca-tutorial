Aula — Observabilidade: logs, métricas e alertas

Desde a fase04, quem indexa um livro é o worker. Quando a indexação esgota as tentativas, a mensagem vai para a fila de mortas e ninguém fica sabendo: o log é texto solto, espalhado em dois processos, nada liga o cadastro às tentativas do worker e não existe um número sequer sobre a API. O que doeu

Na fase04, a indexação de um livro que falha cinco vezes vai para biblioteca:acervo:fila:indice-livros:mortas. O worker escreve uma linha de texto e segue a vida:

log do worker na fase04
worker-1  | Tarefa 1795105373960-0 de biblioteca:acervo:fila:indice-livros foi para a fila de mortas depois de 5 tentativa(s): JSON Parse error: Unexpected identifier "quebrado"
  • Ninguém avisa. Só sabe quem estiver olhando o log do worker naquela hora. O livro fica fora da busca semântica até alguém reclamar que não o encontra.
  • Nada liga as linhas. O app não escreve nada sobre o cadastro; o worker fala de um id de mensagem. Qual requisição publicou aquela tarefa? Quem cadastrou, quando, e o que mais aconteceu na mesma requisição?
  • Texto solto não se filtra. Cada console.log inventa o próprio formato. Para achar todas as falhas de um stream, só com expressão regular e sorte.
  • Nenhum número. Quantas requisições por segundo? Quantas deram 500? Quanto tempo esperam 95% dos leitores? Ninguém sabe.

O guia do curso chama isso de Estágio 11: observabilidade é reduzir o tempo até alguém saber e até entender a causa. Saber vem dos números e do alerta; entender vem dos logs ligados por um id de correlação.

O log estruturado e o traceparent

Um log estruturado é uma linha JSON por evento, sempre com os mesmos campos fixos (time, level, service, msg, trace_id) e depois os campos do caso (book_ids, attempt, error…). A linha deixa de ser uma frase para gente ler e vira um registro para máquina filtrar: “todas as linhas com level error do serviço worker”, “tudo com este trace_id”.

O trace_id é o id de correlação: nasce na borda, a primeira coisa que recebe o pedido, e vai em tudo o que acontece por causa dele. Em vez de inventar um formato, usamos o do cabeçalho traceparent da W3C, o mesmo que o OpenTelemetry lê e escreve:

formato
00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
   trace-id: 32 hex, o pedido inteiro    span-id: 16 hex, este trecho

O trace-id é o mesmo do navegador ao worker; o span-id muda a cada salto (a requisição, cada tentativa do worker). Hoje usamos só o formato, sem biblioteca e sem medir o tempo de cada trecho. Quando o tracing distribuído chegar (Estágio 14 do guia), os ids já estarão no lugar.

O que nunca vai para o log. Senha, token, chave de API, CPF, e-mail, telefone, endereço, o corpo inteiro da requisição “por garantia”. Na dúvida, registre o id, não o dado: "reader_id": 42, nunca o e-mail do leitor. É a invariante I17 do guia: a observabilidade não pode virar o vazamento.

O traceparent

Crie backend/src/infrastructure/trace.ts:

tsbackend/src/infrastructure/trace.ts
import { AsyncLocalStorage } from "node:async_hooks";

/**
 * O id de correlação, no formato traceparent da W3C (o cabeçalho que o
 * OpenTelemetry usa; quando o tracing chegar, ele continua o mesmo trace):
 *
 *   00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
 *      trace-id: a requisição inteira,   span-id: este trecho
 *      do navegador ao worker
 */
const TRACEPARENT = /^00-([0-9a-f]{32})-([0-9a-f]{16})-[0-9a-f]{2}$/;

function randomHex(bytes: number): string {
  return Buffer.from(crypto.getRandomValues(new Uint8Array(bytes))).toString("hex");
}

/** Um trecho novo do trace; sem trace-id, começa um trace novo. */
export function newTraceparent(traceId: string = randomHex(16)): string {
  return `00-${traceId}-${randomHex(8)}-01`;
}

/** O trace-id de um traceparent válido; null se vier malformado ou zerado. */
export function traceIdOf(traceparent: string | null | undefined): string | null {
  const traceId = traceparent?.match(TRACEPARENT)?.[1];
  return traceId && !/^0+$/.test(traceId) ? traceId : null;
}

/**
 * Continua o trace que chegou (no cabeçalho HTTP ou no campo da mensagem da
 * fila) com um span novo, ou começa outro quando não veio nada aproveitável.
 * Nunca lança: um cabeçalho ruim não pode derrubar a requisição.
 */
export function continueTrace(traceparent: string | null | undefined): string {
  return newTraceparent(traceIdOf(traceparent) ?? undefined);
}

// Acompanha a requisição (ou a tarefa da fila) por todos os await, sem passar o
// traceparent de função em função.
const current = new AsyncLocalStorage<string>();

/** Roda fn, e tudo o que ela chamar, dentro deste traceparent. */
export function withTrace<T>(traceparent: string, fn: () => T): T {
  return current.run(traceparent, fn);
}

/** O traceparent de quem está rodando agora; null fora de withTrace. */
export function currentTraceparent(): string | null {
  return current.getStore() ?? null;
}
  • continueTrace é o que a borda chama: com um traceparent válido, mantém o trace-id e gera um span novo; ausente, malformado, zerado ou em maiúsculas, começa um trace novo. Nunca lança: um cabeçalho ruim não pode derrubar a requisição.
  • withTrace e currentTraceparent usam o AsyncLocalStorage (do Node, implementado pelo Bun): o valor acompanha a requisição por todos os await, sem passar o traceparent de função em função. Duas requisições ao mesmo tempo, intercaladas nos await, não se misturam.

O log

Crie backend/src/infrastructure/log.ts:

tsbackend/src/infrastructure/log.ts
import { currentTraceparent, traceIdOf } from "./trace";

type Level = "info" | "warn" | "error";
type Fields = Record<string, unknown>;

/** "app" ou "worker": o compose define SERVICE_NAME em cada serviço. */
const SERVICE = process.env.SERVICE_NAME ?? "app";

// Na suíte (o bun test define NODE_ENV=test), o log fica mudo para não misturar
// centenas de linhas com o resultado dos testes; captureLogs() lê o que sairia.
let write: (line: string) => void = process.env.NODE_ENV === "test" ? () => {} : (line) => console.log(line);

/**
 * Uma linha JSON por evento: time, level, service, msg, o trace_id da
 * requisição ou da tarefa em andamento e os campos do caso.
 *
 * Nunca registre dado pessoal (nome, CPF, e-mail) nem segredo: registre o id.
 */
function emit(level: Level, msg: string, fields: Fields = {}): void {
  const extra = Object.fromEntries(
    Object.entries(fields).map(([key, value]) => [key, value instanceof Error ? value.message : value]),
  );
  const trace_id = traceIdOf(currentTraceparent()) ?? undefined;
  write(JSON.stringify({ time: new Date().toISOString(), level, service: SERVICE, msg, trace_id, ...extra }));
}

export const log = {
  info: (msg: string, fields?: Fields) => emit("info", msg, fields),
  warn: (msg: string, fields?: Fields) => emit("warn", msg, fields),
  error: (msg: string, fields?: Fields) => emit("error", msg, fields),
};

/** Para os testes: guarda as linhas em vez de escrever no terminal. */
export function captureLogs() {
  const raw: string[] = [];
  const previous = write;
  write = (line) => {
    raw.push(line);
  };
  return {
    raw,
    get lines(): Fields[] {
      return raw.map((line) => JSON.parse(line) as Fields);
    },
    restore() {
      write = previous;
    },
  };
}

Quem chama não passa o trace_id: o emit pergunta ao currentTraceparent(). Um Error nos campos vira a sua mensagem, e o JSON.stringify sem indentação garante uma linha só, mesmo com aspas e quebras de linha no texto. Na suíte o log fica mudo; os testes que precisam ler o que sairia usam o captureLogs().

import { expect, test } from "bun:test";
import { continueTrace, currentTraceparent, newTraceparent, traceIdOf, withTrace } from "./trace";

const FORMAT = /^00-[0-9a-f]{32}-[0-9a-f]{16}-01$/;
const RECEIVED = "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01";
const RECEIVED_TRACE_ID = "4bf92f3577b34da6a3ce929d0e0e4736";

test("um traceparent novo segue o formato da W3C e não se repete", () => {
  expect(newTraceparent()).toMatch(FORMAT);
  expect(newTraceparent()).not.toBe(newTraceparent());
});

test("continuar um trace recebido mantém o trace-id e troca o span-id", () => {
  const next = continueTrace(RECEIVED);
  expect(next).toMatch(FORMAT);
  expect(traceIdOf(next)).toBe(RECEIVED_TRACE_ID);
  expect(next).not.toBe(RECEIVED);
});

test("cabeçalho ausente, malformado, zerado ou em maiúsculas começa um trace novo", () => {
  const invalid = [
    undefined,
    null,
    "",
    "lixo",
    "00-00000000000000000000000000000000-00f067aa0ba902b7-01",
    RECEIVED.toUpperCase(),
    RECEIVED.replace(/^00/, "ff"),
  ];
  for (const header of invalid) {
    const next = continueTrace(header);
    expect(next).toMatch(FORMAT);
    expect(traceIdOf(next)).not.toBe(RECEIVED_TRACE_ID);
  }
  expect(traceIdOf("lixo")).toBeNull();
});

test("dentro de withTrace, todo await enxerga o mesmo traceparent; fora, null", async () => {
  expect(currentTraceparent()).toBeNull();
  const seen = await withTrace(RECEIVED, async () => {
    await Bun.sleep(1);
    await Promise.resolve();
    return currentTraceparent();
  });
  expect(seen).toBe(RECEIVED);
  expect(currentTraceparent()).toBeNull();
});

test("duas requisições ao mesmo tempo não misturam os traces", async () => {
  const other = newTraceparent();
  const [a, b] = await Promise.all([
    withTrace(RECEIVED, async () => {
      await Bun.sleep(5);
      return currentTraceparent();
    }),
    withTrace(other, async () => {
      await Bun.sleep(1);
      return currentTraceparent();
    }),
  ]);
  expect(a).toBe(RECEIVED);
  expect(b).toBe(other);
});

Toda requisição com traceparent

A borda da API é um middleware do Hono, registrado antes das rotas: toda requisição passa por ele. Ele continua o traceparent que chegou (ou começa um), roda o resto da requisição dentro do withTrace, devolve o cabeçalho na resposta e escreve uma linha de log de acesso: método, rota, status e duração.

A rota vai como o padrão que respondeu (/api/livros/:q), nunca como a URL (/api/livros/9780134494166). O routePath(c) do Hono dá esse padrão: depois do next(), o Hono aponta para o handler que respondeu. Com o padrão, as linhas da mesma rota se agrupam; no passo 05, ele vira rótulo de métrica, e a URL com o id criaria uma série nova por livro.

O middleware

Edite backend/src/server.ts: o observe, registrado com api.use("*", observe), e o errorResponse, em que o console.error(error) vira uma linha de erro com a pilha. Só o inesperado vira error: um 404 ou um 409 é resposta normal da API, e já sai no log de acesso.

function errorResponse(error: unknown): Response {
  if (error instanceof InvalidInput || error instanceof InvalidValue || error instanceof SyntaxError) {
    return Response.json({ error: error.message }, { status: 400 });
  }

  if (error instanceof NotFound) {
    return Response.json({ error: error.message }, { status: 404 });
  }

  if (error instanceof RuleConflict || error instanceof DomainError) {
    return Response.json({ error: error.message }, { status: 409 });
  }

  if (error instanceof PayloadTooLarge) {
    return Response.json({ error: error.message }, { status: 413 });
  }

  if (error instanceof NotImplemented) {
    return Response.json({ error: error.message }, { status: 501 });
  }

  if (error instanceof ServiceUnavailable) {
    return Response.json({ error: error.message }, { status: 503 });
  }

  // só o inesperado vai para o log como erro; o trace_id liga a linha à resposta
  log.error("erro interno", { error: error as Error, stack: (error as Error)?.stack });

  return Response.json({ error: "Erro interno" }, { status: 500 });
}

/**
 * Toda requisição da API passa por aqui: continua o traceparent recebido (ou
 * começa um), roda o resto dentro dele, devolve o cabeçalho na resposta e
 * registra uma linha de log.
 */
const observe: MiddlewareHandler = (c, next) => {
  const traceparent = continueTrace(c.req.header("traceparent"));
  return withTrace(traceparent, async () => {
    const start = performance.now();
    await next();
    const seconds = (performance.now() - start) / 1000;
    // o padrão da rota que respondeu ("/api/livros/:id"), nunca a URL com o id:
    // depois do next(), o Hono aponta routeIndex para o handler que respondeu
    const route = routePath(c);
    c.header("traceparent", traceparent);
    log.info("requisição", { method: c.req.method, route, status: c.res.status, duration_ms: Math.round(seconds * 1000) });
  });
};

export function createApp(slices: RegisterRoutes[] = []) {
  const api = new Hono();

  api.use("*", observe);

  api.get("/", (context) => context.json({ message: "API da Biblioteca" }));

  for (const registerRoutes of slices) registerRoutes(api);

  const app = new Hono();

  // toda a API mora sob /api: o resto dos endereços fica livre para o frontend
  app.route("/api", api);
  app.all("/api/*", (context) => context.notFound());

  // arquivos do build: index.html, JS, CSS, ícone
  app.use("*", serveStatic({ root: FRONTEND }));

  // qualquer outro endereço (/cadastrar, por exemplo) é rota do React Router:
  // devolve o index.html e o roteador do navegador decide o que mostrar
  app.get("*", serveStatic({ path: `${FRONTEND}/index.html` }));

  app.notFound((context) =>
    context.json({ error: "Recurso não encontrado" }, 404),
  );

  app.onError((error) => errorResponse(error));

  return app;
}

O traceparent atravessa a fila

A fila é uma fronteira assíncrona: o HTTP já respondeu 201, e o trabalho continua em outro processo, segundos ou minutos depois. O AsyncLocalStorage não atravessa a rede; o que não for na mensagem não chega ao worker. O guia diz isso na invariante I16: o id de correlação atravessa logs, cabeçalhos HTTP e metadados da mensagem, e “o rastro se parte exatamente na fronteira assíncrona”.

Publicar e consumir com o trace

Edite backend/src/infrastructure/queue.ts:

  • enqueue, chamado dentro da requisição, põe um campo traceparent no XADD, ao lado de dados.
  • run, no worker, lê o campo e roda a tarefa dentro de withTrace(continueTrace(...)): mesmo trace-id, span novo a cada tentativa. Tudo o que a tarefa registrar sai com o trace_id do cadastro.
  • Cada desfecho vira uma linha: tarefa concluída (info), tarefa falhou; volta para a fila (warn, ainda vai tentar de novo) e tarefa foi para a fila de mortas (error: alguém precisa olhar). Todas com stream, message_id e attempt.
  • A fila de mortas já copiava os campos da mensagem (...fields); agora o traceparent vai junto, e quem abrir a mensagem morta acha o trace.

 * e o rastro não se parte na fila.
 */
export async function enqueue(stream: string, data: unknown, client: RedisClient | null = queue): Promise<string | null> {
  if (!client) return null;
  const fields = ["dados", JSON.stringify(data)];
  const traceparent = currentTraceparent();
  if (traceparent) fields.push("traceparent", traceparent);
  try {
    await ready(client);
    return await client.send("XADD", [stream, "MAXLEN", "~", MAX_LENGTH, "*", ...fields]) as string;
  } catch (error) {
    log.warn("fila indisponível", { stream, error: error as Error });
    return null;
  }
}

/**
 * Cria o grupo de cada stream. Começa do "0", e não do "$": o que foi publicado
 * antes de existir algum worker também é entregue. Criar de novo não é erro.
 */
export async function prepareGroups(jobs: Job[], client: RedisClient): Promise<void> {
  await ready(client);
  for (const job of jobs) {
    try {
      await client.send("XGROUP", ["CREATE", job.stream, GROUP, "0", "MKSTREAM"]);
    } catch (error) {
      if (!/BUSYGROUP/.test((error as Error).message)) throw error;
    }
  }
}

/**
 * Executa uma mensagem dentro do trace de quem a publicou (mensagem sem o
 * campo, de antes desta fase, ganha um trace novo). Só o XACK tira a mensagem
 * da lista de pendentes.
 */
async function run(job: Job, [id, fields]: Entry, deliveries: number, settings: Settings): Promise<void> {
  const { client, maxDeliveries } = settings;
  const field = (name: string) => {
    const at = fields.indexOf(name);
    return at === -1 ? undefined : fields[at + 1];
  };
  const about = { stream: job.stream, message_id: id, attempt: deliveries };
  await withTrace(continueTrace(field("traceparent")), async () => {
    try {
      await job.handle(JSON.parse(field("dados") ?? "null"));
      await client.send("XACK", [job.stream, GROUP, id]);
      log.info("tarefa concluída", about);
    } catch (error) {
      const reason = (error as Error).message;
      if (deliveries < maxDeliveries) {
        // sem XACK, a mensagem continua pendente e volta depois de retryAfterMs
        log.warn("tarefa falhou; volta para a fila", { ...about, error: reason });
        return;
      }
      // desistir também é uma decisão: a mensagem sai da fila, mas não some
      // (...fields leva o traceparent junto para a fila de mortas)
      await client.send("XADD", [deadLetterStream(job.stream), "*", ...fields, "erro", reason, "origem", id]);
      await client.send("XACK", [job.stream, GROUP, id]);
      log.error("tarefa foi para a fila de mortas", { ...about, error: reason });
    }
  });
}

/**
 * Pendentes há mais de retryAfterMs: o worker que as recebeu falhou ou caiu sem
 * confirmar. O XPENDING diz quantas vezes cada uma já foi entregue; o XCLAIM
 * passa a mensagem para este worker e confere de novo o tempo parado, então
 * dois workers nunca pegam a mesma.
 */
async function retryStuck(job: Job, settings: Settings): Promise<number> {
  const { client, consumer, retryAfterMs } = settings;
  const stuck = await client.send("XPENDING", [job.stream, GROUP, "IDLE", String(retryAfterMs), "-", "+", "10"]) as [string, string, number, number][];
  let handled = 0;
  for (const [id, , , deliveries] of stuck) {
    const claimed = await client.send("XCLAIM", [job.stream, GROUP, consumer, String(retryAfterMs), id]) as Entry[];
    for (const entry of claimed) {
      await run(job, entry, deliveries + 1, settings);
      handled++;
    }
  }
  return handled;
}

/** Mensagens novas (">"): nunca entregues a ninguém do grupo. */
async function readNew(jobs: Job[], settings: Settings): Promise<number> {
  const { client, consumer, blockMs } = settings;
  const args = ["GROUP", GROUP, consumer, "COUNT", "10"];
  if (blockMs !== null) args.push("BLOCK", String(blockMs));
  args.push("STREAMS", ...jobs.map((job) => job.stream), ...jobs.map(() => ">"));
  // em RESP3, a resposta é um mapa { stream: [[id, campos], ...] }; null quando nada chegou
  const reply = await client.send("XREADGROUP", args) as Record<string, Entry[]> | null;
  if (!reply) return 0;
  let handled = 0;
  for (const job of jobs) {
    for (const entry of reply[job.stream] ?? []) {
      await run(job, entry, 1, settings);
      handled++;
    }
  }
  return handled;
}

/** Uma volta do worker: primeiro as que ficaram pendentes, depois as novas. */
export async function workOnce(jobs: Job[], options: WorkerOptions): Promise<number> {
  const settings = { ...DEFAULTS, ...options } as Settings;
  await ready(settings.client);
  let handled = 0;
  for (const job of jobs) handled += await retryStuck(job, settings);
  return handled + await readNew(jobs, settings);
}

  const s3 = requireStorage(client);
  try {
    await s3.write(key, bytes, { type });
  } catch (error) {
    throw unavailable(error);
  }
}

/**
 * Lê os metadados (stat) e abre o fluxo de bytes; null se a chave não existe.
 * Não devolva new Response(s3.file(key)): o Bun responderia 302 para uma URL
 * assinada em rustfs:9000, um endereço que o navegador não alcança.
 */
export async function getObject(key: string, client = storage): Promise<StoredObject | null> {
  const file = requireStorage(client).file(key);
  try {
    const { type, size } = await file.stat();
    return { stream: file.stream(), type, size };
  } catch (error) {
    if ((error as { code?: string }).code === "NoSuchKey") return null;
    throw unavailable(error);
  }
}

  } catch (error) {

  }
}

function isUnknownIndex(error: unknown): boolean {
  // Redis 8: "SEARCH_INDEX_NOT_FOUND Index not found"; versões anteriores: "Unknown index name"
  return /index not found|unknown index|no such index/i.test((error as Error).message);
}

/**
 * Garante que o índice existe para este embedder e diz se precisou criá-lo.
 * Vetores de outro modelo não se comparam com os deste: trocar de modelo apaga o
 * índice junto com os documentos (DD) e começa de novo.
 */
export async function ensureBookIndex(embedder: Embedder, client: RedisClient): Promise<boolean> {
  try {
    if (await client.get(INDEX_MODEL) === embedder.id) {
      await client.send("FT.INFO", [INDEX]);
      return false;
    }
    await client.send("FT.DROPINDEX", [INDEX, "DD"]);
  } catch (error) {
    if (!isUnknownIndex(error)) throw error;
  }
  try {
    await client.send("FT.CREATE", [
      INDEX, "ON", "HASH", "PREFIX", "1", KEY_PREFIX,
      "SCHEMA", "embedding", "VECTOR", "HNSW", "6",
      "TYPE", "FLOAT32", "DIM", String(embedder.dimensions), "DISTANCE_METRIC", "COSINE",
    ]);
  } catch (error) {
    // outra requisição criou o índice ao mesmo tempo
    if (/already exists/i.test((error as Error).message)) return false;
    throw error;
  }
  await client.set(INDEX_MODEL, embedder.id);
  return true;
}

/** O que o modelo lê de cada livro: o título e, para dar contexto, o autor. */
function indexText(title: string, authorName: string | undefined): string {
  return authorName ? `${title} — ${authorName}` : title;
}

async function syncIds(ids: number[], integration: CatalogIntegration, embedder: Embedder | null, client: RedisClient): Promise<IndexResult & { created: boolean }> {
  const result = { indexed: 0, removed: 0, created: false };
  const unique = [...new Set(ids)];
  if (unique.length === 0) return result;
  await ready(client);
  const rows = await sql`SELECT id, titulo AS title, autor_id AS "authorId" FROM livros WHERE id IN ${sql(unique)}` as { id: number; title: string; authorId: number }[];

  // remover não precisa de embedder: o livro saiu do Postgres, sai do índice
  const existing = new Set(rows.map((row) => row.id));
  for (const id of unique) {
    if (!existing.has(id)) result.removed += await client.del(bookIndexKey(id));
  }
  if (!embedder || rows.length === 0) return result;

  result.created = await ensureBookIndex(embedder, client);
  const pending: { id: number; text: string }[] = [];
  for (const row of rows) {
    const text = indexText(row.title, (await integration.author(sql, row.authorId))?.name);
    // só paga o embedding quando o texto mudou ou quando o vetor gravado não tem o
    // tamanho deste modelo: o índice recusa esse vetor em silêncio, e ele ficaria para sempre
    const key = bookIndexKey(row.id);
    const sameText = await client.hget(key, "texto") === text;
    const rightSize = await client.send("HSTRLEN", [key, "embedding"]) === embedder.dimensions * 4;
    if (!sameText || !rightSize) pending.push({ id: row.id, text });
  }
  if (pending.length === 0) return result;

  const vectors = await embedder.embed(pending.map((item) => item.text), "document");
  for (const [i, item] of pending.entries()) {
    const vector = vectors[i]!;
    const blob = Buffer.from(vector.buffer, vector.byteOffset, vector.byteLength);
    // send aceita Buffer em tempo de execução; os tipos do Bun só declaram string
    await client.send("HSET", [bookIndexKey(item.id), "texto", item.text, "embedding", blob as unknown as string]);
  }
  result.indexed = pending.length;
  return result;
}

/**
 * O Bun conversa em RESP3, e nele o FT.SEARCH responde um mapa
 * ({ results: [{ id, extra_attributes }] }). Em RESP2 a mesma resposta é uma
 * lista plana: [total, chave, [campo, valor], chave, [campo, valor], ...].
 */
export function parseKnnReply(reply: unknown, keyPrefix: string): KnnHit[] {
  const toHit = (key: string, distance: string) => ({ id: Number(key.slice(keyPrefix.length)), distance: Number(distance) });
  if (Array.isArray(reply)) {
    const hits: KnnHit[] = [];
    for (let i = 1; i < reply.length; i += 2) {
      const fields = reply[i + 1] as string[];
      hits.push(toHit(reply[i] as string, fields[fields.indexOf("distancia") + 1]!));
    }
    return hits;
  }
  const { results } = reply as { results: { id: string; extra_attributes: { distancia: string } }[] };
  return results.map((result) => toHit(result.id, result.extra_attributes.distancia));
}

As métricas em /metrics

Logs contam a história de um pedido; métricas são números somados ao longo do tempo, baratos de guardar e bons para perceber que algo mudou. Para uma API, três perguntas bastam para começar, o método RED:

PerguntaDe onde sai
Rate: quantas requisições por segundo?_count do histograma, com rate()
Errors: quantas deram erro?_count só com status="5.."
Duration: quanto tempo levam?_bucket, com histogram_quantile()

As três saem de um histograma só, http_server_request_duration_seconds, o nome que o OpenTelemetry usa para a duração das requisições HTTP. Um histograma guarda, por baldes, quantas requisições levaram até 5 ms, até 10 ms, até 25 ms… até 10 s. Com os baldes dá para estimar o p95, o tempo que 95% dos leitores não passaram: a média esconde a cauda (90 requisições de 5 ms e 10 de 3 s dão média de 305 ms, um tempo que ninguém esperou).

Para a fila, três gauges (números que sobem e descem), por stream: mensagens aguardando um worker, entregues e não confirmadas, e na fila de mortas. Eles não ficam na memória do worker: o app lê do Redis na hora da coleta (XINFO GROUPS e XLEN), e por isso o worker continua sem abrir porta.

Cardinalidade. Cada combinação nova de rótulos é uma série guardada para sempre. Rótulo com o padrão da rota: dezenas de séries. Rótulo com a URL, o id do leitor, o e-mail ou o trace_id: uma série por valor, até o Prometheus cair. O trace_id mora no log; a métrica só conta.

O módulo das métricas

Crie backend/src/infrastructure/metrics.ts. Sem biblioteca: o formato de texto do Prometheus são linhas nome{rótulos} valor, e o histograma são três famílias (_bucket, _sum, _count).

tsbackend/src/infrastructure/metrics.ts
import type { RedisClient } from "bun";
import { log } from "./log";
import { ready, redisKey } from "./redis";

/**
 * As métricas da aplicação, no formato de texto que o Prometheus lê em /metrics.
 *
 * Um histograma só responde às três perguntas do método RED:
 *   Rate     quantas requisições por segundo?   → _count
 *   Errors   quantas deram erro?                → _count com status="5.."
 *   Duration quanto tempo levam?                → _bucket (p50, p95, p99)
 * O nome é o mesmo que o OpenTelemetry usa para a duração das requisições HTTP.
 */
const NAME = "http_server_request_duration_seconds";

/** Limites dos baldes, em segundos. */
const BUCKETS = [0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10];

type Series = { labels: string; buckets: number[]; sum: number; count: number };

/**
 * Uma série por combinação de rótulos. A rota é o padrão casado pelo Hono
 * ("/api/livros/:id"), nunca a URL: cada valor novo de rótulo é mais uma série
 * guardada para sempre (é a "cardinalidade"). Nada pessoal em rótulo.
 */
const series = new Map<string, Series>();

/** O valor de um rótulo no formato do Prometheus: \, " e quebra de linha escapados. */
function labelValue(value: string): string {
  return value.replace(/\\/g, "\\\\").replace(/"/g, '\\"').replace(/\n/g, "\\n");
}

export function observeRequest(method: string, route: string, status: number, seconds: number): void {
  const labels = `method="${labelValue(method)}",route="${labelValue(route)}",status="${status}"`;
  let current = series.get(labels);
  if (!current) series.set(labels, (current = { labels, buckets: BUCKETS.map(() => 0), sum: 0, count: 0 }));
  // cumulativo: uma requisição de 30 ms conta em "até 50 ms" e em todos os maiores
  BUCKETS.forEach((limit, i) => {
    if (seconds <= limit) current.buckets[i]!++;
  });
  current.sum += seconds;
  current.count++;
}

export function renderHttpMetrics(): string {
  const lines = [`# HELP ${NAME} Duração das requisições HTTP da API, em segundos.`, `# TYPE ${NAME} histogram`];
  for (const { labels, buckets, sum, count } of series.values()) {
    BUCKETS.forEach((limit, i) => lines.push(`${NAME}_bucket{${labels},le="${limit}"} ${buckets[i]}`));
    lines.push(`${NAME}_bucket{${labels},le="+Inf"} ${count}`, `${NAME}_sum{${labels}} ${sum}`, `${NAME}_count{${labels}} ${count}`);
  }
  return lines.join("\n") + "\n";
}

const DEAD_SUFFIX = ":mortas";

/** Todos os streams deste ambiente (prefixo do REDIS_PREFIX) no Redis da fila. */
async function streamsOf(client: RedisClient): Promise<string[]> {
  const keys: string[] = [];
  let cursor = "0";
  do {
    const [next, batch] = await client.send("SCAN", [cursor, "MATCH", redisKey("*"), "TYPE", "stream", "COUNT", "500"]) as [string, string[]];
    keys.push(...batch);
    cursor = next;
  } while (cursor !== "0");
  return keys.sort();
}

/**
 * Gauges da fila, lidos do Redis na hora da coleta (o worker não precisa abrir
 * porta): por stream, quantas mensagens aguardam um worker, quantas foram
 * entregues e não confirmadas, e quantas estão na fila de mortas. Sem fila, ou
 * com ela fora do ar, devolve "" e as métricas HTTP saem assim mesmo.
 *
 * Com a fila caindo, o cliente fica tentando reconectar e o comando não volta:
 * por isso o limite de tempo, bem abaixo dos 5 s que o Prometheus espera pela
 * coleta inteira. Sem ele, a coleta estoura e o histograma some junto.
 */
export async function renderQueueMetrics(client: RedisClient | null, timeoutMs = 1500): Promise<string> {
  if (!client) return "";
  let timer: Timer | undefined;
  const giveUp = new Promise<never>((_, reject) => {
    timer = setTimeout(() => reject(new Error(`a fila não respondeu em ${timeoutMs} ms`)), timeoutMs);
  });
  try {
    return await Promise.race([queueGauges(client), giveUp]);
  } catch (error) {
    log.warn("métricas da fila indisponíveis", { error: error as Error });
    return "";
  } finally {
    clearTimeout(timer);
  }
}

async function queueGauges(client: RedisClient): Promise<string> {
  await ready(client);
  const waiting: string[] = [];
  const pending: string[] = [];
  const dead: string[] = [];
  for (const key of await streamsOf(client)) {
    if (key.endsWith(DEAD_SUFFIX)) continue;
    const label = `{stream="${labelValue(key)}"}`;
    const groups = await client.send("XINFO", ["GROUPS", key]) as { name: string; lag: number | null; pending: number }[];
    const group = groups.find((g) => g.name === "workers");
    waiting.push(`queue_messages_waiting${label} ${group ? (group.lag ?? 0) : await client.send("XLEN", [key])}`);
    pending.push(`queue_messages_pending${label} ${group?.pending ?? 0}`);
    dead.push(`queue_dead_letters${label} ${await client.send("XLEN", [key + DEAD_SUFFIX])}`);
  }
  const gauge = (name: string, help: string, values: string[]) => [`# HELP ${name} ${help}`, `# TYPE ${name} gauge`, ...values];
  return [
    ...gauge("queue_messages_waiting", "Mensagens publicadas e ainda não entregues a um worker.", waiting),
    ...gauge("queue_messages_pending", "Mensagens entregues a um worker e ainda não confirmadas.", pending),
    ...gauge("queue_dead_letters", "Mensagens na fila de mortas: alguém precisa olhar.", dead),
  ].join("\n") + "\n";
}

/** Para os testes: começa do zero. */
export function resetMetrics(): void {
  series.clear();
}

Com a fila fora do ar, a parte da fila sai vazia e o /metrics continua respondendo com o histograma. Para isso serve o limite de 1,5 s: com a fila caindo, o cliente fica tentando reconectar e o comando não volta. function errorResponse(error: unknown): Response {
  if (error instanceof InvalidInput || error instanceof InvalidValue || error instanceof SyntaxError) {
    return Response.json({ error: error.message }, { status: 400 });
  }

  if (error instanceof NotFound) {
    return Response.json({ error: error.message }, { status: 404 });

  if (error instanceof RuleConflict || error instanceof DomainError) {
    return Response.json({ error: error.message }, { status: 409 });
  }

  if (error instanceof PayloadTooLarge) {
    return Response.json({ error: error.message }, { status: 413 });
  }

  if (error instanceof NotImplemented) {
    return Response.json({ error: error.message }, { status: 501 });

    observeRequest(c.req.method, route, c.res.status, seconds);
  });
};

Prometheus, Grafana e alertas

Números em /metrics são só o valor de agora. O Prometheus vem buscá-los a cada 5 s (o modelo pull: a aplicação não sabe quem a lê) e guarda cada leitura com a hora, uma série temporal. Se o app cair, a coleta falha e o próprio Prometheus registra up = 0: o silêncio também vira número. O Grafana desenha o painel e avalia as regras de alerta, consultando o Prometheus em PromQL.

Um painel sem alerta é decoração: ninguém fica olhando o dia inteiro. As três regras vigiam sintomas, o que o leitor sente, e não causas (CPU alta, Redis reiniciou):

RegraPromQLDispara
Tarefas na fila de mortasmax(queue_dead_letters) > 0na primeira avaliação: uma tarefa perdida já é problema
Leitores recebendo errosum(rate(http_server_request_duration_seconds_count{status=~"5.."}[1m])) > 0se a taxa continuar acima de zero por 20 s. Como o rate olha o último minuto, até um 500 solto dura isso: aqui, qualquer 5xx avisa. Para ignorar erro solto, a condição ganharia um limite (mais de 1% das requisições, por exemplo)
API fora do armax(up{job="biblioteca"}) < 1se a coleta falhar por 30 s: um restart rápido do contêiner não avisa. Com o app fora, o leitor recebe “conexão recusada”, e não 5xx, e a regra de cima fica calada

Cada regra também diz o que fazer sem dado, quando a consulta volta vazia (noDataState). Nas mortas, KeepLast: com a fila fora do ar o gauge some, e falta de dado não é boa notícia; um [RESOLVED] falso seria pior que nada. Nos 5xx, OK: sem nenhum erro, a série nem existe. No up, Alerting: se nem ele existe, o Prometheus não está coletando o app.

O compose

Edite infra/compose.yaml: os serviços prometheus e grafana, com versões fixas e portas presas ao 127.0.0.1. O Grafana entra direto como leitor, sem login; para editar, Sign in com admin / biblioteca. Os e-mails saem pelo SMTP do Mailpit (porta 1025, dentro da rede), e o GF_SERVER_ROOT_URL faz o link do e-mail abrir o Grafana: sem ele, o Grafana monta os links com localhost:3000, a porta dele dentro do contêiner, que no seu computador é o app.

  app:
    build:
      context: ..
      dockerfile: infra/Dockerfile
    environment:
      # dentro da rede do compose, o banco atende pelo nome do serviço: db
      DATABASE_URL: postgres://biblioteca:biblioteca@db:5432/biblioteca
      # e o Redis, pelo nome redis; o prefixo separa as chaves da aplicação das dos testes

      REDIS_PREFIX: biblioteca
      # vem de infra/.env (copie infra/.env.example); vazia, a busca semântica fica indisponível
      GEMINI_API_KEY: ${GEMINI_API_KEY:-}

      S3_ENDPOINT: http://rustfs:9000
      S3_ACCESS_KEY_ID: biblioteca
      S3_SECRET_ACCESS_KEY: biblioteca-secreta
      S3_BUCKET: biblioteca

      QUEUE_URL: redis://fila:6379
      # e o provedor de e-mail, pelo nome mailpit (sem fila, o app envia na hora)
      EMAIL_URL: http://mailpit:8025
      # o campo "service" de cada linha do log estruturado
      SERVICE_NAME: app

      - "3000:3000"

        condition: service_healthy
      fila:
        condition: service_healthy
      mailpit:
        condition: service_healthy
      storage-init:
        condition: service_completed_successfully

  # Não publica porta: ninguém chama o worker, ele é quem busca trabalho na fila.
  # docker compose -f infra/compose.yaml up -d --scale worker=2 sobe dois.
  worker:

      context: ..

      NODE_ENV: test

      S3_SECRET_ACCESS_KEY: biblioteca-secreta
      S3_BUCKET: biblioteca-test

      # hora, e a suíte não depende de um worker rodando. Os testes da fila e do

      TEST_QUEUE_URL: redis://fila:6379

    # serviços deste infra/compose.yaml o enxergam, pela rede interna do Docker

  # propósito: ele só guarda dados derivados. Se o contêiner sumir, o servidor
  # reconstrói tudo a partir do Postgres, que continua sendo a fonte da verdade.
  redis:
    image: redis:8
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 2s
      timeout: 3s
      retries: 15

  # A fila: o mesmo Redis 8, com outro papel. O cache guarda o que dá para
  # recalcular; a fila guarda trabalho que ainda não foi feito. Por isso aqui há
  # volume, cada escrita vai para o disco (appendonly) e, sem memória, o Redis
  # recusa o XADD em vez de apagar uma tarefa para abrir espaço (noeviction).
  # Sem "ports": só o app e o worker falam com ela, pela rede do compose.
  fila:
    image: redis:8
    command: ["redis-server", "--appendonly", "yes", "--maxmemory-policy", "noeviction"]
    volumes:
      - filadata:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 2s
      timeout: 3s
      retries: 15

  # RustFS: armazenamento de objetos compatível com S3, onde ficam as imagens.
  # Ao contrário do Redis, aqui há volume: os bytes de uma capa só existem nele.
  # A API S3 (9000) não tem porta publicada; só o console web, em
  # http://localhost:9011/rustfs/console/, para você ver os objetos chegando.
  rustfs:
    image: rustfs/rustfs:1.0.5
    environment:
      # o "usuário" e a "senha" do S3, só para desenvolvimento, como os do Postgres
      RUSTFS_ACCESS_KEY: biblioteca
      RUSTFS_SECRET_KEY: biblioteca-secreta
    ports:
      - "127.0.0.1:9011:9001"
    volumes:
      - rustfsdata:/data
    healthcheck:
      # /health/ready, e não /health: o /health responde 200 antes de a API S3
      # aceitar requisições, e ela devolve 503 nos primeiros segundos
      test: ["CMD-SHELL", "curl -fsS http://127.0.0.1:9000/health/ready >/dev/null"]
      interval: 2s
      timeout: 3s
      retries: 30

  # Tarefa única: cria os buckets da aplicação e dos testes com o rc, o cliente
  # de linha de comando que vem dentro da imagem do RustFS. O S3Client do Bun lê e
  # grava objetos, mas não cria buckets. Rodar de novo não dá erro.
  storage-init:
    image: rustfs/rustfs:1.0.5
    depends_on:
      rustfs:
        condition: service_healthy
    entrypoint: ["/bin/sh", "-c"]
    command:
      - |
        set -e
        rc alias set local http://rustfs:9000 biblioteca biblioteca-secreta
        rc bucket create --ignore-existing local/biblioteca
        rc bucket create --ignore-existing local/biblioteca-test

  # Mailpit: um provedor de e-mail de mentira, só para desenvolvimento. Recebe
  # pela API HTTP (POST /api/v1/send), como os provedores de verdade, e mostra
  # cada mensagem numa caixa de entrada web, em http://localhost:8025, sem
  # entregar nada a ninguém. Sem volume: reiniciar o contêiner esvazia a caixa.
  mailpit:
    image: axllent/mailpit:v1.34.0
    ports:
      - "127.0.0.1:8025:8025"
    healthcheck:
      test: ["CMD", "/mailpit", "readyz"]
      interval: 2s
      timeout: 3s
      retries: 15

  # Prometheus: vem buscar o /metrics do app a cada 5 s e guarda cada número com
  # a hora em que foi lido (uma série temporal). Sem volume: o histórico some
  # com o contêiner, o que basta para desenvolver. Em http://localhost:9090.
  prometheus:
    image: prom/prometheus:v3.16.0
    volumes:
      - ./observability/prometheus.yml:/etc/prometheus/prometheus.yml:ro
    ports:
      - "127.0.0.1:9090:9090"
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:9090/-/ready"]
      interval: 2s
      timeout: 3s
      retries: 15

  # Grafana: o painel e os alertas, em http://localhost:3001. Tudo vem de
  # arquivos de observability/grafana/: fonte de dados, painel, regras e para
  # quem mandar o e-mail (o SMTP do Mailpit, na porta 1025).
  grafana:
    image: grafana/grafana:13.3.2
    environment:
      # entra direto como leitor, sem login; para editar, "Sign in" com
      # admin / biblioteca. Senha no compose só porque a porta está presa ao
      # 127.0.0.1: num servidor de verdade, nunca.
      GF_AUTH_ANONYMOUS_ENABLED: "true"
      GF_SECURITY_ADMIN_PASSWORD: biblioteca
      GF_SMTP_ENABLED: "true"
      GF_SMTP_HOST: mailpit:1025
      GF_SMTP_FROM_ADDRESS: grafana@biblioteca.local
      GF_SMTP_FROM_NAME: Grafana da biblioteca
      # os links do e-mail apontam para cá (sem isto, para localhost:3000, que é o app)
      GF_SERVER_ROOT_URL: http://localhost:3001
    volumes:
      - ./observability/grafana/datasource.yaml:/etc/grafana/provisioning/datasources/datasource.yaml:ro
      - ./observability/grafana/dashboards.yaml:/etc/grafana/provisioning/dashboards/dashboards.yaml:ro
      - ./observability/grafana/biblioteca.json:/var/lib/grafana/dashboards/biblioteca.json:ro
      - ./observability/grafana/alertas.yaml:/etc/grafana/provisioning/alerting/alertas.yaml:ro
    ports:
      - "127.0.0.1:3001:3000"
    depends_on:
      prometheus:
        condition: service_healthy
      mailpit:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:3000/api/health"]
      interval: 2s
      timeout: 3s
      retries: 30
      # na primeira subida o Grafana cria o próprio banco: pode passar de 1 min
      start_period: 3m

Fechamento e produção

O que cada passo ensinou

  • 01: log é dado, não frase. Campos fixos, nada pessoal, e um id de correlação num formato que já existe.
  • 02: o id nasce na borda e volta para quem pediu; a rota entra como padrão, nunca como URL.
  • 03: o rastro se parte na fronteira assíncrona, a menos que a mensagem o leve.
  • 04: msg fixa, o que varia em campo. Metade estruturado é ainda texto solto.
  • 05: um histograma responde ao RED; o p95 mostra a cauda que a média esconde; rótulo de métrica não leva id.
  • 06: o Prometheus vem buscar, o Grafana desenha e avisa, e tudo é arquivo no repositório. Alerte o sintoma.
  • 07: o alerta encurta o tempo até saber; o trace_id, o tempo até entender.

Em produção

  • Os logs vão para um lugar só. docker compose logs | grep serve com dois contêineres numa máquina. Com dez réplicas em três máquinas, um coletor (Loki, Elasticsearch, o serviço do provedor de nuvem) junta as linhas e indexa os campos. O formato JSON desta aula é o que essas ferramentas esperam.
  • Retenção e volume custam dinheiro. Uma linha por requisição, vezes milhões, é disco e fatura. Equipes definem por quanto tempo guardar e às vezes amostram o nível info, nunca o error.
  • O /metrics não fica público: porta interna ou autenticação. E os baldes do histograma acompanham a meta de tempo de resposta: se a meta é 300 ms, precisa haver um balde perto de 300 ms.
  • Alertas têm dono e plantão. Com muitas regras e várias equipes, entra o Alertmanager (ou o roteamento do Grafana) para mandar cada alerta para quem cuida daquela parte, agrupar e silenciar durante uma manutenção.

O que ficou de fora

  • Tracing distribuído. Hoje o traceparent só carrega o número; não medimos quanto tempo cada trecho levou nem desenhamos a linha do tempo. Entra quando a requisição atravessar vários serviços (Estágio 14 do guia): o OpenTelemetry lê o mesmo cabeçalho, e os ids desta aula continuam valendo. Num monólito, é o antipadrão 8 do guia.
  • Métricas do próprio worker, como o tempo de cada tarefa. Entra quando o tempo de processamento importar tanto quanto a profundidade da fila; aí o worker abre uma porta interna ou empurra os números para um gateway.
  • SLO e orçamento de erro. Em vez de “qualquer 500 por 20 s”, uma meta como “99,5% das requisições em menos de 300 ms no mês”, e alertas pela velocidade com que o orçamento está sendo gasto. Entra quando houver um compromisso de nível de serviço com alguém.
  • Um painel por módulo. O painel desta aula é da aplicação inteira. Com mais tráfego, cada módulo (Acervo, Circulação, Autoria) ganha o seu, com as métricas de negócio que importam para ele.
